## 3. Fiabilité — le sujet dominant

### F1 🔴 Le pipeline nocturne est destructif et non transactionnel

`src/multilane.py:75-81` appelle `db.init_matchups_table()` et `db.init_synergies_table()` au **démarrage** du run — soit `DROP TABLE IF EXISTS` puis `CREATE`. La base est donc vidée, puis re-remplie pendant **~45 minutes** de scraping.

```
21:27  DROP matchups / DROP synergies
21:27→22:12  566 pages scrapées (5 lanes × 2 phases)
22:12  premier moment où la base est de nouveau complète
```

Toute interruption dans cette fenêtre — crash Firefox, coupure réseau, retour de Cloudflare, arrêt du PC, `Ctrl+C` — laisse une base **amputée**, sans sauvegarde ni rollback possible. C'est précisément le mécanisme du sinistre du 01/06/2026 (40 753 → 16 179 matchups). Le contrôle de complétude ajouté en H1 constate les dégâts *après coup*, il ne les empêche pas : au moment où il s'exécute, les anciennes données sont déjà détruites.

Le chemin du menu 3 fait exactement la même chose (`db.init_matchups_table()` + `db.init_champion_scores_table()` avant de scraper) : les deux orchestrateurs partagent ce risque, et c'est le plus utilisé qui l'exécute le plus souvent.

**Ce qui manque** : écrire dans des tables de staging (ou une copie du fichier `.db`), valider, puis basculer en une transaction. Ou, a minima, copier `data/db.db` avant le `DROP` et restaurer si le run échoue.

### F2 🔴 Deux orchestrateurs divergents — le chemin utilisé est le moins outillé

Il existe deux façons de mettre à jour les données, et elles ne font pas le même travail :

| Log fichier | ❌ (console uniquement) | ✅ |
| Notifications | ❌ | ✅ |

Le menu 3 est donc un chemin de scraping **légitime et à jour** — ce n'est pas du code legacy mono-lane — mais il court-circuite quatre des cinq garde-fous construits en Horizon 1. Conséquence directe : la base est fraîche (25/08) alors que tous les indicateurs du projet la datent du 16/07.

**Et il détruit les scores avant de les recalculer.** Le menu appelle `db.init_champion_scores_table()` — soit `DROP TABLE champion_scores` — au *début* du run, puis `assistant.calculate_global_scores()` à la fin. Le 25/08, ce recalcul a levé un `AttributeError` sur chaque champion (bug corrigé le jour même par `08d2c9c`, avec test de régression). Le fix est en place, mais **le recalcul n'a jamais été relancé depuis** :

- `champion_scores` : **0 ligne** ⇒ menu « tier list » inutilisable (`[ERROR] No champion scores found in database`) ;
- `pool_ban_recommendations` : 528 lignes, jamais rafraîchies par ce chemin ;
- `db_meta` : vide ⇒ voir F3.

Le geste correctif est trivial (relancer le seul recalcul, sans re-scraper) ; ce qui compte, c'est que **rien n'a signalé la panne pendant 4 jours** — c'est le même angle mort que F3.

*Pour mémoire, le dernier run de `update_all.py` (16/07) s'était lui aussi arrêté avant les étapes dérivées, sur un `COMPLETENESS CHECK FAILED` : 566/566 pages scrapées, mais 13 champions sur 173 sortis avec 0 synergie. Voir F6 — le contrôle est tout-ou-rien.*

### F3 🔴 Le garde-fou de fraîcheur ne mesure pas le scrape

`src/data_freshness.py:63-72` : si `db_meta.last_update_utc` est absent — ce qui est le cas dès qu'on met à jour par le menu (F2) — il retombe sur `path.stat().st_mtime`. Or `data/db.db` est modifié par l'application elle-même à chaque session (pools, bans, écritures diverses). L'indicateur mesure donc la dernière **ouverture** de la base, pas sa dernière **mise à jour**.

Aujourd'hui, il donne par chance le bon ordre de grandeur. Le 16/07 → 25/08, il aurait affiché :

```
[OK] Données : 26 398 matchups, 21 288 synergies — mises à jour il y a 1 h (estimé via date du fichier)
```

…sur des données de six semaines. Le garde-fou construit précisément pour empêcher la répétition du silence de mars-juin 2026 produit un « tout va bien » qui n'est jamais faux au bon moment. C'est le défaut le plus insidieux du lot : il ne signale rien **et** il inspire confiance. Il m'a moi-même trompé dans l'autre sens.

**Correctif de fond** : (1) écrire `db_meta` sur le chemin réellement utilisé, c'est-à-dire à la fin du scrape lui-même plutôt que dans l'orchestrateur, avec un statut distinct selon que les étapes dérivées ont abouti ; (2) supprimer le repli sur le `mtime` — en l'absence de métadonnée, afficher « fraîcheur inconnue », que le code traite déjà comme obsolète.

### F5 🟠 Aucune contrainte d'unicité : 1 263 doublons en base

Le schéma n'a ni `UNIQUE(champion, enemy, lane)` ni `ON CONFLICT`. Vérification SQL :

- **1 263** triplets `(champion, enemy, lane)` en double dans `matchups` ;
- **783** dans `synergies` ;

### F6 🟠 Le contrôle de complétude est tout-ou-rien

`assert_completeness()` lève dès qu'un seul champion est sous le seuil. Comme le scraping d'une page échoue de temps en temps par nature (site tiers), le pipeline est structurellement fragile : **1 champion sur 173 suffit à jeter 45 minutes de travail et à laisser les dérivés périmés**. Il manque une distinction entre :

- **bloquant** : volumétrie globale effondrée, > 5 % des champions vides (le sinistre du 01/06) ;
- **avertissement** : quelques champions incomplets → on continue, on recalcule les scores, on notifie, et on relance un repair ciblé automatiquement.

## 4. Métier — la qualité des recommandations

C'est la section la plus riche en gisements de valeur, parce que l'infrastructure de juin a produit des données que le moteur n'exploite pas encore.

### M1 🔴 La lane est collectée mais jamais lue

Recherche exhaustive : la colonne `lane` n'apparaît dans **aucun** fichier de `src/analysis/`, ni dans `draft_monitor.py`, ni dans `assistant.py`, ni dans l'UI. Elle n'est utilisée que par le pipeline d'écriture (`multilane.py`, `parallel_parser.py`, `repair_data.py`), par les index, et par `pool_manager` pour composer les pools système.

À la lecture, deux comportements coexistent, aucun n'étant lane-aware :

- `get_champion_matchups_by_name()` retourne **toutes les lignes**, doublons de lane compris. Pour Swain, 376 lignes pour 99 ennemis distincts : le scoring voit quatre fois chaque ennemi (bottom, middle, support, top mélangés).
- `get_matchup_delta2()` agrège par moyenne pondérée aux games — ce qui noie un matchup de lane dans les autres.

**Mesure de ce que ça coûte** (SQL sur la base réelle) :

| Champion | delta2 moyen pondéré par lane |
|---|---|
| Pantheon | top **+0,303** · jungle +0,050 · support **−0,081** |
| Swain | support +0,020 · top +0,016 · middle −0,057 · bottom **−0,148** |
| Yasuo | bottom +0,170 · middle +0,140 · top **−0,033** |
| Seraphine | bottom **+0,079** · support **−0,100** |

Et au niveau du matchup individuel, l'écart entre lanes pour une même paire monte à :

```
Ivern vs Aphelios          23,9 pts de delta2
Quinn vs Belveth           23,0
Heimerdinger vs Yasuo      22,9
Rammus vs MissFortune      18,6
```

Autrement dit : **l'information la plus discriminante de la base est systématiquement moyennée avant d'atteindre le joueur.** Quand le draft coach conseille Pantheon, il ne sait pas si c'est le Pantheon top (+0,30) ou le Pantheon support (−0,08).

**Portée retenue (décision @pj35, 29/08)** : le Live Coach doit déterminer la lane **de chacun des 10 joueurs**, alliés et adversaires, pour affiner les calculs. C'est plus ambitieux que la simple lecture de sa propre lane, et ça change la nature du problème : il ne s'agit plus seulement de filtrer une requête, mais d'**inférer une assignation de rôles** à partir d'informations partielles. Trois sources, par ordre de fiabilité :

1. **Position assignée par le client** — `assignedPosition` est présent dans la session de champion select pour l'équipe alliée en file classée. `src/lcu_client.py` ne l'expose pas encore. Fiable quand disponible, absent en Draft Normal / ARAM / certaines files.
2. **Distribution de lanes du champion pické** — déjà en base : la table `matchups` porte la lane, et `lane_discovery` connaît la part de parties par lane. Un champion pické est un indice probabiliste sur son rôle (Pantheon : 55 % support / 35 % top / 10 % jungle, par exemple).
3. **Contrainte d'unicité des rôles** — une équipe a exactement un joueur par rôle. C'est ce qui transforme cinq devinettes indépendantes en un problème d'**affectation optimale** (chaque champion à un rôle distinct, en maximisant la vraisemblance globale). À cette taille, il n'y a que `5! = 120` affectations possibles : les énumérer toutes donne l'optimum exact en moins d'une milliseconde, sans aucune dépendance. C'est nettement plus juste que « chaque champion prend sa lane la plus fréquente », qui produit des équipes à deux junglers et zéro support.

L'ordre de pick apporte un signal supplémentaire mais faible (les premiers picks sont plutôt top/jungle/mid) — à ne considérer qu'en départage.

Le tout doit rester **révisable** : les lanes inférées s'affichent, le joueur peut les corriger, et l'assignation se recalcule à chaque nouveau pick (l'information s'affine à mesure que le draft avance).

### M2 🔴 Deux chemins de calcul donnent deux résultats différents

| Fonction | Traitement des lanes multiples | Utilisée par |
|---|---|---|
| `get_matchup_delta2()` | moyenne pondérée par games (Python) | `score_against_team`, chemin unitaire |
| `get_all_matchups_bulk()` | **écrasement** : `cache[(champ, enemy)] = delta2`, dernière ligne SQL gagnante | trio holistique, cache d'`Assistant`, warm cache |

Mesure : 26 398 lignes en base → **15 699 entrées** dans le cache bulk. **10 699 valeurs sont jetées silencieusement**, et la valeur conservée dépend de l'ordre de parcours SQL — donc arbitraire (elle peut être la lane la moins jouée du champion).

Conséquence : le même matchup peut être noté différemment selon qu'on passe par le draft coach unitaire ou par l'optimiseur de trio. C'est une incohérence de résultat, pas seulement de style.

### M3 🟠 Deux notions distinctes portées par une seule pondération

**Précision apportée par @pj35** : la pondération par `pickrate` n'est pas là pour mesurer la qualité de la donnée, mais pour **prédire le pick adverse**. Quand le score d'un champion est calculé face à des slots ennemis encore vides, pondérer chaque matchup par la fréquence de pick de l'ennemi revient à calculer une espérance sur les adversaires probables. C'est un choix de modélisation juste, et il faut le conserver.

Le constat se reformule donc ainsi : **deux notions différentes sont portées par le même poids.**

| Notion | Question posée | Grandeur pertinente | État actuel |
|---|---|---|---|
| Probabilité de rencontre | « quelle chance ai-je d'affronter ce champion ? » | `pickrate` | ✅ modélisée, correctement |
| Confiance dans l'estimation | « ce `delta2` est-il mesuré ou bruité ? » | `games` | ❌ seuil binaire à 200, puis ignorée |

Le filtre est binaire (`pickrate >= 0.5 AND games >= 200`) et, au-delà du seuil, **un matchup à 210 parties pèse exactement autant qu'un matchup à 26 354** (les deux extrêmes réels de la base ; moyenne : 1 326). Sur un `delta2` typique de ±0,1 à ±3 points, le bruit d'échantillonnage à 200 parties est du même ordre de grandeur que le signal : le coach recommande parfois du bruit avec l'assurance d'un fait établi.

Le correctif ne consiste pas à remplacer une pondération par l'autre, mais à les **composer** : `poids = pickrate × confiance(games)`, où `confiance(games) = games / (games + k)` fait tendre les petits échantillons vers 0 (leur `delta2` est alors ramené vers la valeur neutre, pas supprimé). Un seul paramètre `k` à calibrer, valeur de départ raisonnable : `k ≈ 500`.

Enfin, rien de tout cela n'est visible : le nombre de parties n'apparaît **nulle part** dans les recommandations du draft coach (cf. U5).

### M4 🟠 La conversion delta2 → « % de winrate » est l'identité, mais présentée comme un pourcentage

`ChampionScorer.delta2_to_win_advantage()` (`src/analysis/scoring.py:104-137`) : 34 lignes de docstring pour `advantage = delta2 * 1.0`, avec un paramètre `champion_name` inutilisé (conservé « pour compatibilité »). L'UI affiche ensuite `+2,34 %` et le libelle « win rate advantage ».

Le raisonnement d'origine (février 2026) s'appuyait sur « l'analyse de 36 000+ matchups » — base qui n'existe plus. La conversion n'a jamais été revalidée depuis, ni sur la base mono-lane, ni sur la base multi-lane actuelle. Soit on la revalide empiriquement, soit on cesse d'afficher une unité de pourcentage pour un score relatif.

### M5 🟠 `calculate_team_winrate` n'a pas de fondement probabiliste — proposition de modèle

**État actuel.** Moyenne géométrique des winrates individuels, bornée arbitrairement à [25 %, 75 %], commentée comme « more mathematically sound than arithmetic averaging ». Multiplier des winrates ne modélise rien ici : ce ne sont ni des probabilités indépendantes, ni des événements conjoints — les cinq joueurs gagnent ou perdent **la même** partie. Le résultat est un indice arbitraire présenté comme un « team winrate ». Même problème pour `delta2_to_win_advantage` (M4), qui affiche un `delta2` brut avec un signe `%`.

**Ce que veut @pj35** : un modèle cohérent. Voici le cadre standard, celui utilisé par Elo, Bradley-Terry et toute la famille des modèles de prédiction de match. Il tient en une idée.

#### L'idée : raisonner en log-odds, pas en probabilités

Les probabilités ne s'additionnent pas (60 % + 60 % n'a aucun sens) et se multiplient mal. Leur **logit** — le logarithme de la cote — s'additionne naturellement :

```
logit(p) = ln( p / (1 - p) )        logit(0,50) = 0
sigmoid(x) = 1 / (1 + e^(-x))       l'inverse : ramène un score dans ]0 ; 1[
```

On part d'un match équilibré (`logit = 0`), chaque élément du draft ajoute ou retranche un « avantage » exprimé sur cette échelle, et la sigmoïde finale reconvertit la somme en probabilité :

```
avantage_total = Σ (contributions alliées) − Σ (contributions adverses)
P(victoire)    = sigmoid(avantage_total)
```

Deux propriétés qu'on obtient gratuitement, et qui sont exactement ce qui manque aujourd'hui : **le résultat reste toujours dans ]0 ; 1[** (plus besoin du clamp à [25, 75]), et **les avantages saturent** — accumuler des avantages fait progresser la probabilité de moins en moins vite, ce qui est le comportement réel d'un draft.

#### La conversion « point de winrate → log-odds »

Autour de 50 %, la relation est quasi linéaire :

```
d(logit)/dp = 1 / (p(1−p)) = 4   à p = 0,5

⇒ +1 point de winrate (0,01) ≈ +0,04 en log-odds
```

C'est cette constante (`≈ 0,04`) qui remplace le `delta2 * 1.0` de M4 : elle donne un sens à l'unité au lieu d'afficher un score brut avec un signe `%`.

#### Application au draft

```
score = Σ_alliés  [ 0,04 × (winrate_base_i − 50) ]        # force intrinsèque
      + Σ_matchups [ 0,04 × k_m × delta2_ij ]             # nos matchups contre eux
      + Σ_synergies[ 0,04 × k_s × delta2_ik ]             # nos synergies internes
      − (les mêmes termes pour l'équipe adverse)

P(victoire) = sigmoid(score)
```

Trois remarques importantes :

- **Pas de double comptage.** La winrate de base d'un champion contient déjà l'effet *moyen* de ses adversaires ; `delta1`/`delta2` de LoLalytics sont précisément des **écarts à cette moyenne**. Les additionner est donc légitime — c'est même le seul découpage qui l'est.
- **`k_m` et `k_s` (~0,3 à 1) corrigent le double comptage résiduel** entre matchups qui se recouvrent. Ils remplacent le `SYNERGY_BONUS_MULTIPLIER` actuel, avec la même fonction mais une échelle interprétable.
- **Le modèle est calibrable.** C'est son principal avantage sur l'existant : le draft coach connaît, via le LCU, l'issue réelle de chaque partie. En journalisant `(probabilité prédite, résultat)`, on peut vérifier la calibration (« sur mes drafts annoncés à 60 %, j'en gagne combien ? ») et ajuster `k_m`, `k_s` par régression logistique. Une centaine de parties suffit à corriger grossièrement, quelques centaines à affiner. Aucun paramètre n'a besoin d'être deviné définitivement.

#### Chemin d'implémentation suggéré

1. Écrire `logit`/`sigmoid` et la constante de conversion dans `ChampionScorer` (~15 lignes).
2. Remplacer `calculate_team_winrate` par ce calcul ; supprimer le clamp [25, 75].
3. Faire passer `delta2_to_win_advantage` par la même conversion (règle M4 au passage).
4. Journaliser prédiction + résultat à la fin de chaque partie.
5. Calibrer `k_m`, `k_s` quand assez de parties sont accumulées.

Les étapes 1 à 3 sont mécaniques et sans risque (les tests de régression existants encadrent le comportement). Les étapes 4 et 5 sont ce qui fait passer l'outil d'un score maison à une prédiction vérifiable — c'est le seul endroit du projet où l'on peut mesurer si le coach a *raison*.

### M6 🟡 Asymétrie dans `score_against_team`

Notre avantage est dilué sur les 5 slots ennemis (les picks inconnus sont remplis avec `avg_delta2`), alors que l'avantage adverse est une moyenne simple sur les **seuls** ennemis déjà connus. Documenté dans le code comme un choix, mais l'effet net est que le score du premier pick n'est pas comparable à celui du dernier — ce que l'interface ne signale pas.

### M7 🟡 Comparaison sensible à la casse dans les synergies

`calculate_synergy_bonus()` : `[s for s in synergies if s.ally_name in ally_names]` — comparaison exacte, alors que tout le reste du code normalise en minuscules (`m.enemy_name.lower()`). Toute variation de casse dans la liste d'alliés fait silencieusement tomber le bonus de synergie à 0.

### M8 🟡 Seuils métier hors configuration

Malgré la règle « `config_constants.py` pour toute valeur hardcodée » :

| Valeur | Emplacement |
|---|---|
| `games >= 200`, `pickrate >= 0.5` | 3 requêtes SQL de `src/db.py` (`get_matchup_delta2`, `get_all_matchups_bulk`, `get_all_synergies_bulk`) |
| `pickrate > 0.5` | `get_champion_matchups_by_name` |
| `sum(m.games) >= 500` | `src/draft_monitor.py:884` (seuil d'éligibilité d'un champion aux recommandations) |
| Top 3 recommandations | `src/draft_monitor.py:903` |

Ces valeurs dupliquent — et peuvent contredire — `analysis_config.MIN_MATCHUP_GAMES` et `MIN_PICKRATE`.

## 5. Performance

### P1 🟠 Chaque page LoLalytics est chargée deux fois — ⭐ priorisé par @pj35

Le pipeline fait deux passes complètes : d'abord les matchups pour les 283 couples (champion, lane), puis les synergies pour les mêmes 283 couples. Or les deux jeux de données sont **sur la même page** — le scraper clique simplement le bouton « Common Teammates » pour basculer l'affichage (`XPathConfig.SYNERGIES_BUTTON_XPATH`).

Mesure du run du 16/07 :

| Phase | Durée |
|---|---|
| Matchups (5 lanes) | 24,7 min |
| Synergies (5 lanes) | 18,1 min |
| Découverte de lane | 6 s |
| **Total** | **45 min** |

Fusionner les deux extractions en une seule visite de page économiserait l'intégralité des chargements de page de la seconde passe — estimation **30 à 40 % du temps total**, soit ~28-30 min. Bénéfice secondaire : moitié moins de requêtes vers le site tiers, donc moitié moins d'exposition à un blocage.

(Pour mémoire, le README annonce toujours « 12 min avec 10 workers » : c'était le temps d'un scrape **mono-lane** avec 10 workers, avant la réduction à 5 workers et avant le multi-lane. Le chiffre réel est 45 min.)

### P2 🟡 Requête SQL dans la boucle des trios

`_evaluate_trio_holistic()` appelle `self.db.get_all_champion_names()` à **chaque** trio évalué. Pour un pool de 15 champions : 455 trios × une requête + construction de dict de 173 entrées. À sortir de la boucle (le pré-chargement `get_all_matchups_bulk` juste au-dessus montre que le pattern est connu).

### P3 🟡 Double calcul dans l'affichage des recommandations

`_provide_recommendations()` calcule `matchup_score` et `synergy_score` pour tous les champions du pool, trie… puis **recalcule** les deux scores pour chacun des 3 affichés. Coût modeste, mais surtout : si un calcul devenait non déterministe, l'affichage divergerait du classement.

### P4 🟡 `COLLATE NOCASE` sur les jointures

`get_matchup_delta2` filtre avec `c1.name = ? COLLATE NOCASE`, ce qui empêche l'utilisation de l'index sur `champions.name`. Mesure : **6,3 ms par appel** (200 appels en 1,27 s) sur une base de 26 k lignes — c'est ~50× plus lent qu'attendu pour une lecture indexée. Le draft coach en fait 5 par champion de pool et par changement d'état.

### P5 🟢 Points sains à préserver

- `get_all_matchups_bulk()` : 0,05 s pour 15 699 entrées ; `get_all_synergies_bulk()` : 0,08 s. Le problème N+1 historique est bien réglé.
- 14 index, dont les 4 composites lane créés en H1.
- Priorité de processus `BELOW_NORMAL` pendant le scrape nocturne — bonne attention.
- Découverte de lane en HTTP pur plutôt qu'en Selenium : 173 champions en 6 secondes.

## 6. Expérience utilisateur

### U1 🟠 Six questions avant chaque session de draft coach

À chaque lancement : auto-hover ? auto-accept queue ? auto-ban hover ? onetricks ? poids synergie/matchup ? puis choix du pool parmi 11. **Aucune préférence n'est mémorisée** — alors que dans les faits, les réponses sont presque toujours les mêmes. Un fichier de préférences (ou la réutilisation des derniers choix avec confirmation en une touche) supprimerait 30 secondes de friction avant chaque partie, au moment exact où le joueur est pressé.

### U2 🟠 Interface bilingue involontaire

Le menu principal, les messages `[ERROR]`/`[INFO]` et les conseils de draft sont en anglais ; la bannière de fraîcheur, le prompt de poids de synergie et les notifications Discord sont en français. Pour un utilisateur unique francophone, autant trancher (le français, cf. la décision « outil personnel ») — ou au minimum ne pas mélanger dans le même écran.

### U3 🟡 Emojis en console, malgré l'interdiction documentée

`data_freshness.py` explique en commentaire que les emojis font planter les consoles cp1252 et utilise donc `[OK]`/`[ALERTE]`. Mais `draft_coach_ui.py` (`🎯 🔥 🚫 🌐`), `assistant.py` (`✅ ⚠️`) et `draft_monitor.py` en émettent librement. Le risque d'`UnicodeEncodeError` en sortie redirigée est réel et déjà identifié par le projet lui-même.

### U4 🟡 Deux orchestrateurs aux garanties différentes

Le menu 3 « Parse Match Statistics » scrape correctement en multi-lane, mais sans contrôle de complétude, sans `db_meta`, sans recalcul des bans et sans log fichier (détail en F2). L'utilisateur n'a aucun moyen de savoir que le chemin qu'il emprunte offre moins de garanties que celui documenté. Les deux doivent converger — le plus simple étant que le menu appelle `update_all.py`, qui reste l'implémentation de référence.

### U5 🟡 Aucun indicateur de confiance dans les recommandations

Affichage actuel : `[1st] Pantheon +2,34% (Matchup: +1,80%, Synergy: +0,54%)`. Rien n'indique sur combien de parties repose ce chiffre, ni sur quelle lane, ni si l'écart avec le 2ᵉ est significatif. C'est le complément naturel de M1 et M3, et c'est peu coûteux : les données sont déjà là.

## 9. Lecture d'ensemble

Quatre observations pour orienter le tri :

**1. Le chantier principal est l'exploitation des lanes, et il est déjà à moitié payé.** Les données sont en base depuis juillet, taguées, indexées, propres — et personne ne les lit. Le compléter par l'inférence des rôles des 10 joueurs (M1) est le seul item du backlog qui change la *nature* du conseil rendu, pas seulement sa présentation. Tout le reste sert à ce que ce conseil repose sur des données saines.

**2. Le projet n'a pas un problème d'outillage, il a un problème de chaînage.** Tout ce qu'il faut pour un pipeline fiable existe et est testé — découverte de lane, contrôle de complétude, métadonnées de fraîcheur, notifications, runbook — mais le chemin réellement emprunté (le menu) n'en branche qu'une partie. Faire converger les deux orchestrateurs et recalculer les scores, c'est peu de code pour beaucoup de fiabilité retrouvée.

**3. Rien dans le système ne sait dater ses propres données.** C'est la cause racine de F2 et F3, et le meilleur révélateur du problème : j'ai conclu à des données de six semaines alors qu'elles avaient quatre jours, avec la base sous les yeux et tous les logs accessibles. Un outil d'aide à la décision qui ne peut pas dater ses entrées ne peut pas non plus signaler qu'il a cessé d'être à jour.

**4. La dette technique se re-contracte plus vite qu'elle ne se rembourse.** Le dépôt a maigri de 12 800 lignes tout en voyant ses quatre monolithes grossir de 1 248 lignes. Tant que la couverture reste mesurée sur `src/analysis` seul, rien ne freine cette dérive sur le cœur du produit. Élargir la mesure (quitte à abaisser temporairement le seuil) est un prérequis peu coûteux à toute reprise du démantèlement.
